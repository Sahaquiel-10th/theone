# ONE Launcher / Bridge 在线安全更新计划

状态：执行中

适用范围：首批普通 FAT32 + MBR ONE Key，以及随后使用同一协议的硬件 Key

目标：已经交付的 ONE Key 不必寄回；用户在 ONE 页面确认更新后，当前电脑上的 Bridge 安全更新 U 盘里的对应启动器。

## 1. 不变的产品结论

- 在线更新必须完整通过 [ONE Key 在场体验硬约束](./ONE-KEY-PRESENCE-INVARIANT.md)；不能为了更新牺牲拔插自动恢复或制造重复 Bridge。
- ONE Key、Launcher、Bridge、灌装器是四个不同组件。
- Key 保存身份凭证；Launcher 是用户双击的入口；Bridge 是驻留在当前电脑、证明 Key 在场并承接本机能力的进程；灌装器只负责出厂写盘。
- 更新以操作系统为单位进行：Mac 更新 Mac 启动器，Windows 更新 Windows 启动器。另一端会在该系统下次使用时更新。
- 网页在检测到新版时显示简洁提醒；最新版不显示提醒。
- 用户确认后才安装。更新过程不得修改、复制、上传或重新签发 `.one/credential.json`。
- 更新失败必须保留旧版可启动能力；不得让一次网络中断把 Key 变成不可用。
- 普通 U 盘只是当前原型载体，不宣传为不可复制的安全硬件；本协议不依赖未来的芯片方案。

## 2. 安全边界

- 每个发布清单使用独立的 Ed25519 发布私钥签名；私钥不进入仓库、服务器应用环境或 U 盘。
- Launcher 内只内置发布公钥。
- 清单签名覆盖版本、平台、架构、下载地址、文件大小和 SHA-256。
- Bridge 只接受 HTTPS 更新地址，并在安装前同时校验清单签名、平台/架构、文件大小和 SHA-256。
- 网页不能传入任意下载地址；它只能要求 Bridge 安装服务端已经验证并发布的稳定版本。
- 更新请求必须同时满足：当前账号会话有效、Key 属于当前 Workspace、当前电脑上的 Key 在场并完成即时签名证明。
- 服务端记录更新请求和结果，但不记录设备私钥、凭证正文或下载内容。

## 3. 更新链路

1. Bridge 建立在线连接时上报平台、架构、Launcher 版本和更新协议版本。
2. ONE 服务端读取并验证已签名的稳定版清单。
3. 网页请求当前 Key 的版本状态；只有 `latest > current` 时显示更新提醒。
4. 用户点击更新，服务端先向当前 Bridge 发起 Key 在场挑战，再发送对应平台的更新任务。
5. Bridge 下载到临时目录并完成全部校验。
6. Bridge 在 U 盘中暂存新版，保留旧版备份，使用同卷原子重命名替换对应启动器。
7. Bridge 启动新版驻留进程；新版重新连上服务端后，页面确认成功。
8. 若下载、校验、替换或启动失败，恢复旧版并报告失败原因。

## 3.1 网站版本与启动器版本

- 网站/服务端和 Launcher/Bridge 是两条独立发布线，版本号不需一致。
- 网站代码通过 Git 和生产部署流程上线；启动器通过独立签名包发布，不要为只更新启动器而重新构建网站。
- 首次启用更新通道时，发布器写入非敏感路径/公钥配置并重启一次 ONE 服务。之后发布新签名包不需重新部署网站，也不需重启服务；服务端在查询时读取当前稳定版清单。
- 网页在进入工作区和页面重新回到前台时查询当前 Bridge 版本。只有服务端已发布更高的适配版本才显示提醒；最新版不显示。
- 发布包未完整上传、签名/摘要校验失败或服务器没有启用更新通道时，网页必须保持无提醒，不得发布半成品。

## 4. 组件改动

### 服务端

- 增加严格的签名清单解析、版本比较和缓存。
- WebSocket 在线状态保存平台、架构、版本、更新协议。
- 增加当前用户的更新状态接口与发起更新接口。
- 将更新任务精确绑定到 `deviceId + installationId`，禁止跨电脑或跨 Workspace 调度。
- 增加更新审计事件和不泄露内部路径的错误响应。

### Web

- 增加全局但不过度打扰的“ONE 可以更新”提示。
- 点击后显示下载、校验、安装、完成或失败状态；防止重复点击。
- Key 未插入、旧版不支持在线更新时给出明确动作，不显示技术旁白。

### Mac Launcher / Bridge

- 上报 `macos + arm64/x86_64 + version + protocol`。
- 验证 Ed25519 清单和包 SHA-256。
- 使用签名后的 `.app` 压缩包暂存安装，并再次执行系统代码签名校验。
- 只替换 `ONE for Mac.app`，不触碰 Windows 文件和凭证目录。

### Windows Launcher / Bridge

- 上报 `windows + amd64 + version + protocol`。
- 使用 Go 标准库验证 Ed25519 清单和 EXE SHA-256。
- 只替换 `ONE for Windows.exe`，保留一个可恢复备份，不触碰 Mac 文件和凭证目录。

### 发布与灌装

- 增加可复现的双平台构建、打包、签名清单和发布脚本。
- 发布私钥由运营离线保管；CI/服务器只接收签好的制品。
- 灌装器在出厂验收中确认两个启动器都声明支持更新协议。
- 第一批批量灌装前，必须完成一次真实的“旧版本 → 新版本”Mac 与 Windows 双机测试。

## 6. 首批发货门槛

以下项目没有全部通过，不批量发货：

- Key 插着可登录和发消息，拔掉后的下一次受保护请求在调用模型/知识库前被拦截。
- 更新失败后旧 Launcher 仍能启动。
- 任一平台更新都不改变凭证文件的字节内容和权限预期。
- 普通用户不能看到其他用户、其他 Workspace 或超管的版本/更新状态。
- 挂失 Key 不能查询或执行更新。
- Mac 与 Windows 各完成至少一次真实升级，不只依赖单元测试。

## 7. 暂不纳入本轮

- 芯片级 Key 固件与硬件 OTA。
- 无人值守强制更新。
- 差分包、灰度比例、多个发布频道和大规模 CDN。
- Local Agent、Codex、WorkBuddy 自身的更新与安装。
- 从网页直接写入浏览器下载目录后假装完成自动更新。

## 8. 首批执行顺序

1. 先上线兼容旧 Launcher 的服务端与网页更新入口，不发布新版清单。
2. 只灌装一块 `0.3.0` 测试 Key，确认 Mac、Windows 的登录、在场校验和聊天仍正常。
3. 将已经离线签名并验证的 `0.3.1` 测试包发布到服务器稳定版目录。
4. 在 Mac 与 Windows 各点击一次网页更新，核对只替换当前平台启动器、凭证字节不变，失败回滚可用。
5. 完成拔插、休眠、挂失和跨 Workspace 回归后，把出厂版本提升为已验证的 `0.3.1`。
6. 用提升后的版本批量灌装首批 Key；不要让正式收件人第一次打开就先升级。
