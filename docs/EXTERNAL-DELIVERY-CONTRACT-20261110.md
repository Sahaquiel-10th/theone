# 外部接口交付与后台完整性契约

2026-11-10 用户确认。本文件是外部成果交付的当前规范，优先于此前将严格全文或格式核对作为保存完成门槛的方案。代码、发布和实际服务验收分别记录，本文本身不代表已上线。

## 用户目标

ONE 先保留自己的完整成果，再将成果交付到用户指定的平台。远端确认本次写入成功后，用户立即取得原稿与外部成果入口。后台检查独立运行，检查暂未完成、格式变化或平台附加内容均不把已确认的交付改回“任务未完成”。

用户侧流程为“完整成果已留存 → 外部写入确认成功 → 返回成果入口 → 保存步骤完成”。后台流程为“检查源内容是否被覆盖 → 临时读取故障有限重试 → 具体缺失或无法判断时给出对应说明”。

## 三类事实独立记录

| 事实 | 可证明的内容 | 对用户的意义 |
| --- | --- | --- |
| ONE 原稿 | 完整正文及其来源、摘要和版本已持久化 | 用户始终能从 ONE 取回本次完整成果 |
| 外部交付 | 本次操作的可信成功回执与精确成果标识或入口已绑定 | 可以报告已保存，完成该写入步骤 |
| 后台完整性 | 已读取结果覆盖了哪些源内容，是否缺失或无法判断 | 独立质量检查，可有提醒或后续处理 |

工作流仍按必需步骤推进。一个 Notion 保存步骤完成不会证明后续网页、文件、发布或其他独立目标已经完成。后继步骤消费自己真正需要的成果，如完整 ONE 原稿或已确认的页面入口，避免为了获得页面入口等待排版一致。

## 成功回执的要求

- 在发送前持久化原稿引用、输入摘要、目标绑定和写入断点。
- 将成功回执绑定到精确 `workspaceId`、`userId`、operation、checkpoint、本次正文和目标。旧页面存在、旧成功记录或模型口头声明不能充当新写入回执。
- 同步接口须返回适配器已审定的业务成功结果。异步接口须等原任务查询返回成功，并取得可定位的成果标识。HTTP 接受、入队或异步 pending 仍属于处理中。
- 响应丢失时记录交付未知，沿原 operation、幂等键或异步任务查询。缺少可证明安全的重放能力时，恢复只读取原结果。
- 只读核对也可证明实际成果已经存在。该证明保留其来源，历史上没有收到写入回执的事实继续保留。
- 成功交付与通知分别持久化。通知失败只补通知，重启与重复事件复用同一成果。
- 同一任务多次保存时，每个步骤保留自己的成功回执、原稿摘要和对应完整源成果。最新一次回执轮换不能抹掉前一步的交付证据。冻结证据仍验证所属账号、操作、目标和正文，不能借用旧成功状态完成新步骤。

## 分段覆盖检查

检查从 ONE 的精确源内容出发，按顺序确认远端是否包含这些内容。远端允许增加日期、标题装饰、说明或额外块。样式分段、Markdown/HTML 等价表达及经适配器解析的传输封装不应造成整单失败。

| 检查结果 | 含义 | 后续行为 |
| --- | --- | --- |
| 覆盖完整 | 源内容在远端按序存在，关键值与引用保持 | 安静结束后台检查，可提供已核对说明 |
| 确切缺失 | 已完整读取目标，能指出源段落、代码、金额或链接等内容未被覆盖 | 给出缺失位置、数量与原稿入口，形成独立处理事项 |
| 暂无法判断 | 读取失败、分页未完整、未知块或无法安全解析 | 有限重试读取，耗尽后说明检查尚未完成 |

匹配须覆盖整份源内容，保留源段落顺序和重复次数。不能仅凭字数、首尾、抽样或一次短片段命中就判整稿完整。表格单元格、数字、代码和链接的业务值各自检查，平台多出的内容不能抵消源内容缺失。标题可能由独立页面属性承载，适配器负责把可证明的标题与正文组成待检查成果。

Notion 草稿优先采用源稿标题作为页面标题。任务编号用于定位执行记录。平台给标题附加日期等装饰可容忍，回读标题仅剩任务编号时应记录标题问题，保存交付与标题质量分别显示。

同页更新也要组合实际标题属性与正文。源稿首标题已被移入页面标题时，经同一安全标题规则确认后参与完整性检查，日期装饰不会被当作缺正文。标题暂未读到时保留无法判断，不能声称该标题已经缺失。两个只读恢复入口使用同一适配逻辑，历史原稿摘要继续保留。

传输层 JSON、MCP 外壳和分页由平台适配器解码。正文中由用户创作的 JSON、代码示例与标签继续作为正文，不能因形似外壳而自动去除。

## 重试与修复

- 临时读取错误在既有授权下自动退避，次数、期限与检查租约持久化。重启、轮询和前端重新连接不重置计数。
- 确定性内容差异进入差异判断，重复相同比较不当作网络恢复。
- 已确认交付保持完成。后台差异使用独立提醒，说明是可查看的格式变化、确切缺失还是暂无法判断。
- 确切缺失可以提出修复。自动再次写入需要原授权仍有效、精确原操作及目标绑定、远端最新版本或全文 CAS、幂等与重试上限，且能证明不会覆盖用户或协作者的新编辑。条件不足时先提供原稿与具体问题，由用户选择处理。
- 本轮 Notion 改造先完成独立后台检查与问题反馈。自动补写须在对应能力和验收齐备后单独开放。

## 平台无关边界

所有新建或修改的外部成果接口采用以上语义。连接器声明其业务成功证据、成果定位方式、只读查询方式、分页及完整性限制、幂等支持、取消能力和安全重放条件。调度层消费这些事实，不包含各平台 Markdown 或响应格式补丁。

知识读取、模型生成、文件生成和外部写入各有成果契约。读取接口以实际可用数据作为成果，财务结算与权限变更仍满足各自独立规则。统一交付语义不授予新平台、新工具、公开分享或新用户数据访问权限。

本轮落地 Notion 的交付与后台检查。已有其他连接器按原权限运行，后续接入或修改时逐项适配本契约，不能把文档更新当作所有平台均已完成改造和实测。

## 历史迁移

1. 保留原始 receipt、正文摘要、比较版本、检查记录和失败历史。
2. 对已有可信成功回执且精确绑定的保存，恢复其已交付事实与原成果入口。旧核对耗尽作为后台检查历史保留。
3. 对仅有页面链接或未知回执的旧任务，先走原结果只读恢复。跨账号、错目标、缺源证据或已取消的运行不得凭新规则被判成功。
4. 恢复只结算已证明的保存步骤，后续独立失败仍按自身状态显示。重复恢复与通知不增加模型调用或外部写入。
5. 后续新写入使用当前内容检查协议。旧规范摘要保持原义，覆盖检查另记检查类型和结果，不篡改历史摘要来凑匹配。

## 实施顺序

1. 以现行主分支建立隔离工作树，备份当前前端及源码。
2. 接通成功写入回执到工作流完成与用户成果入口，后台检查独立调度。
3. 增加源内容分段覆盖检查，分别处理附加内容、确切缺失与读取不确定。
4. 更新任务详情、任务动态和主对话投影，已交付成果不受后台检查结果回退。
5. 迁移有精确成功证据的旧任务，验证未知写入与跨账号反例。
6. 对齐当前架构、API、数据模型、连接器指南和历史规范入口，按下表验收后发布。

## 验收标准

| 场景 | 必须观察到的结果 |
| --- | --- |
| 同步写入成功，回读一直延迟 | 保存步骤和任务按实际必需步骤完成，原稿与真实链接可用，检查留在后台 |
| 异步仅受理，随后成功或失败 | 受理阶段显示处理中，成功后交付，失败时保留原稿和具体保存状态 |
| 远端添加前后缀、日期或块 | 源内容按序覆盖时通过，任务状态保持完成 |
| 粗体分段、链接样式移动或合法传输封装 | 由适配器及内容检查识别，避免格式导致保存失败 |
| 缺中间段、重复段不足、段落重排 | 不误判完整，报告具体源块或范围 |
| 金额、代码、链接或表格值变化 | 记录确切差异，平台附加内容不抵消缺失 |
| 未知块、截断或读取超时 | 检查暂无法判断，有限自动读取后给明确状态 |
| 回执丢失、重复事件、断线或重启 | 查询原结果，无重复生成、收费或写入 |
| 新一轮保存与旧核对交错 | 旧检查不覆盖新成果、页面绑定或状态 |
| 用户或协作者已修改远端 | 保留最新编辑证据，未经安全 CAS 不自动补写 |
| 撤权、停止、跨用户或跨空间 | 拒绝新读取和恢复，旧记录不被借用 |
| 保存成功但后续独立步骤失败 | 保存保持完成，整体准确指出后续失败步骤 |
| 后台核对晚到、失败或通知重送 | 已完成交付保持完成，同一结果按版本去重汇报 |

发布验收分别记录本地测试、跨 Workspace 回归、TypeScript、构建、差异检查、CI、线上版本与实际服务结果。实际服务验收使用新合成稿，核对一次写入、可取回的 ONE 原稿、外部入口、后台结果和主对话终态。业务原稿恢复采用只读方式，单独列证。

## 已知风险与判定纪律

成功回执证明平台承认本次写入，后台检查仍可能发现内容问题。附加内容可能带来业务影响，允许附加表达不代表其事实或质量已被认可。无法安全判断时保留“检查暂无法判断”，并向用户提供 ONE 原稿。

已有失败中既有格式表示差异，也有补存重新写稿或控制字段误入正文。不能统一归为“只是多了几个符号”。每次诊断结合该轮精确原稿、回执和实际回读证据，分别记录交付与质量问题。
