## 本次已确认的故障

原任务的工作流模型输出为 `returned`，长 2,114 个字符。完整输出含 `outcome/content/summary` 外壳，`content` 字符串中存在真实换行，原解析器在 JSON 解析失败后把整段当作正文。后续 Notion 步骤保存了完整外壳。

Notion 回读为 2,116 个字符。移除首尾花括号前的两处格式转义后，SHA-256 与写入前持久保存的原文摘要完全一致。原页面内容已经写入，旧 v9 比较器仍对这两处等价转义判为 `body_mismatch`，三次回读均停止在同一个确定性差异上。

同时存在两条独立缺口。

- 成功写入回执与完整正文核对共用最终状态，核对失败后写入事实也被描述成未知。
- 前端后台快照、回执和详情读取共用错误通道。一次后台读取失败出现全局红条，下次快照成功又可清掉其他读取仍未恢复的错误。

此前回归覆盖了逐个已知格式案例，缺少“异常模型封套 → 保存 → 平台转义 → 回读 → 通知”的组合用例。单项通过不足以证明完整保存链路可靠。

横向检查还发现三个入口问题。

- 新比较版本需要同时用于用户补充原页链接的恢复入口，旧稿的普通回读与原页链接回读均须重新验证精确原稿证据。
- 连续保存时，后续保存必须绑定自己的断点和正文，无法沿用上一笔写入的成功回执。
- 本次“没写到 notion 里啊？”未被识别为复用成稿的保存补充，默认流程又调用模型整理，实际产生了第二版稿件。补存入口需要覆盖这句真实反馈，并保留单纯询问状态、明确改稿、新材料和多源歧义的边界。

## 实施范围

1. 在服务器引导的模型输出边界识别准确的三字段结果。仅对字符串内的换行和制表符做无损 JSON 词法修复。含歧义引号等无法准确解析的控制封套保留输出并停止后续保存。普通文章及文章里的 JSON 示例保持原文语义。
2. 新增版本化的正文比较规则。按文本语法识别等价转义，保留代码、链接目标、段落结构和实际正文差异。旧回执只在精确来源、摘要和写入断点均匹配后采用新规则。
3. 独立记录、验证并公开成功写入回执事实。工作流的执行与验证分别表达，内容核对继续决定最终完成状态。
4. 区分后台读取健康与业务提交失败，每个读取只清除自己的问题。恢复后的进度继续显示已经受理的任务。
5. 补齐已有成稿的补存分支，按同一账号、操作、原消息和摘要复用正文。普通状态询问只返回状态。旧版任务中已由服务端指导的模型最终封套，也在同一边界解析一次。功能产出的普通文章或 JSON 数据继续遵循各自原有契约。

## 实际服务验收追加发现

1. Notion 将一整段加粗拆成相邻 `<b>` 片段，并将链接外的加粗移入链接标签。v10 的类型树保留了容器分段，文字与完整样式覆盖相同时仍不相等。新增 v11 按可见叶子的样式覆盖比较，保留链接目标、代码原始值、块结构和局部样式范围。已发布的 v2–v10 摘要规则保持原义。新增 320 个等价组合与 320 个实际变化反例，并固定本次合成期望正文和真实序列化回读。
2. 同一验收中，模型仍在正常生成，主对话曾短暂显示“内部问题，已停止”，随后完成。这次定位到恢复投影将正在执行的 started 断点提前判成未知结果。修复仅在当前进程确实持有同账号、同任务、同操作的 active 运行时采用正在执行投影。重启后的持久 running 状态、取消及用户停止继续按实际证据处理。实际 service 延迟模型回归覆盖运行中、完成、重启、取消与跨账号。
3. 旧版 save_existing 回执的重新证明不能依赖本次操作里存在写稿步骤。统一复用原稿解析器，以持久原消息、账号归属、消息摘要、正文摘要、工作流断点和 sourceArtifact 的精确绑定重新取得原稿，随后校验旧回执的原始长度及全部摘要。来源缺失、改变或不属于当前账号时拒绝升级证明。
