# ONE 多平台连接交接说明

本文给负责知识平台接入的开发窗口使用。目标是让 ONE 成为统一入口：用户只表达需求，ONE 负责选择合适的知识来源并把结果交给模型；用户不需要理解底层平台、接口或凭证细节。

## 一、不可改变的产品与架构边界

- ONE 是多租户工作台。所有用户数据、授权事务、连接配置和召回结果都必须服务端绑定 `workspaceId`，并在服务端校验当前用户对该 workspace 的成员关系。
- 浏览器传来的 `workspaceId` 只能作为请求参数，不能作为授权依据。
- 聊天路由不能直接请求第三方 HTTP、CLI 或 MCP。每个平台必须实现经过审核的 Connector adapter，由统一的连接层调用。
- 不允许任意 URL、任意 MCP server、任意工具名或动态代码注册到生产环境。平台白名单、API 路径、工具名和数据范围都必须在代码或受控配置中明确。
- 第三方凭证绝不能进入浏览器、URL、客户端包、普通日志或模型上下文。上游原始错误也要脱敏。
- V0.1 采用实时按需召回，不把第三方资料复制到 ONE。后续若要同步，另做 list/get/sync 方案和数据保留策略，不要提前把 V0.1 改成通用知识库。

## 二、平台接入路线（按优先级）

1. **官方 OAuth / Device Flow**：首选。用户在官方页面登录自己的账号并授权，ONE 只接收短期授权结果或可刷新的令牌。
2. **官方 CLI 的授权协议或官方托管 API**：当 CLI 已经提供稳定、合规的用户授权入口时，可以复用其协议；不要求用户在电脑上安装 CLI，服务端可按官方协议实现同等流程。
3. **官方 MCP**：适合平台已经提供标准化、只读能力且有清晰 OAuth/托管方式的情况。ONE 仍需封装 MCP，只暴露审核过的工具。
4. **普通 API Key / 受限 HTTP API**：最后考虑。必须确认 Key 的归属、权限、轮换、服务端托管和多租户隔离；不能因为接口简单就把平台账号凭证交给浏览器。

有 CLI 或 MCP 不等于可以直接执行任意命令或调用任意工具。接入前必须确认：授权主体是个人、企业还是 ONE；权限范围；凭证有效期和刷新方式；是否允许服务端代持；读写能力；平台的会员或计费要求。

## 三、得到大脑：已验证的样本与关键教训

得到大脑是当前已验证的第一个连接器，经验只能作为样本，不能直接泛化给其他平台。

### 3.1 为什么之前会出现“只有一个账号能授权”

早期方案把某个用户自己的 Client ID 当成所有人的授权入口。这样得到会把授权请求看成发给该应用所有者或不匹配的应用，结果是应用所有者可以成功，其他账号在确认阶段失败；页面常把多种上游错误统一显示为“授权码无效”。

官方 CLI 使用得到官方内置的生产 OAuth 应用，用户直接登录并授权自己的得到账号，不需要每个用户自行创建开发者应用。此前用 CLI 验证过：原先失败的会员账号可以登录，语义搜索可以返回结果。ONE 已复用官方 CLI 对应的 Device Flow / OAuth 协议和官方生产 Client ID 默认值；ONE 服务端直接实现协议，没有把 CLI 安装到生产服务器。

相关线上修复已在提交 `cdc0a62` 中完成。后续修改得到连接时，先阅读 `docs/得到大脑官方CLI授权接入说明.md` 和 `docs/2026-09-05-CONNECTION-VALIDATION.md`。

### 3.2 授权流程必须满足

- 授权码来自得到，不由 ONE 自己生成；授权 URL 中的 code 必须与轮询请求使用的 code 完全一致。
- Device Flow 要处理 `authorization_pending`、`slow_down`、`server_error`、用户拒绝、过期、已消费和网络重试；不能把所有失败都归因于“授权码错误”。
- device code、user code、PKCE verifier 等属于短期一次性事务，服务端加密保存并设置过期时间；成功或拒绝后立即作废，防止重放。
- 收到授权结果后先安全持久化，再进行真实的只读验证，避免验证失败触发重复消费授权码。
- 授权成功后只保存加密后的得到连接凭证。凭证属于账号/workspace，不属于某台电脑，也不写入 U 盘。
- 会员资格、scope 不足、HTTP 200 但业务失败，都要转成脱敏的可诊断状态；日志只保留 request id、阶段和上游错误代码，不写 token 或完整 response。

### 3.3 当前允许的得到能力

ONE 当前只需要连接验证和语义召回。官方 CLI 本身权限较宽，可能包含读取、搜索、新建、修改、删除笔记以及标签、知识库管理等能力；CLI 可用不代表 ONE 应开放这些写入权限。后续若要写入，必须单独评审权限、确认交互和审计方案。

## 四、MCP 接入经验

官方 MCP 往往能提供搜索、笔记、知识库、标签或转写等多种工具，但 MCP 返回的工具描述、内容、链接和错误都视为不可信输入。

- `@getnote/mcp` 当前仍要求 API Key + Client ID 配置，不能自动替代用户授权；不要把它误认为“装上 MCP 就能完成个人账号 OAuth”。
- 对每个平台建立固定工具白名单。例如只读 Notion 连接器只允许 `notion-search`、`notion-fetch`、`notion-ai-search`，不把其他工具透传给聊天模型。
- 连接层负责超时、重试、取消、响应大小限制、错误脱敏和结果规范化；聊天路由只拿标准化的 `KnowledgeResult`，不认识平台 API 细节。
- MCP/第三方内容可能包含提示注入，不能让来源文本改变系统权限、workspace、工具白名单或计费规则。

## 五、凭证与数据安全

- API Key、access token、refresh token、Client Secret 必须只在服务端加密保存；加密上下文至少绑定 workspace、provider 和字段用途。
- 授权事务中的 device code、user code、PKCE verifier 也要短期、单次、加密持久化。
- 任何 API 都不得返回第三方凭证，不得把凭证拼进 URL，不得写入日志、错误追踪或前端 bundle。
- 得到或其他平台的连接失败不得 fallback 到另一个 workspace 的连接；无知识模式可以降级，但不能串租户。
- 召回记录、引用和计费事件也要带 workspaceId。跨 workspace 隔离需要单元测试和集成测试覆盖。

## 六、ONE Key、跨设备和连接器的关系

- U 盘是 ONE 身份和在场证明，不是第三方知识平台凭证。U 盘插着时，用户可以正常登录、对话和调用已授权连接；拔出后下一次受保护请求应快速拦截，已开始的原子请求可以完成；重新插入后应自动恢复，不需要重新授权知识平台。
- 得到授权是账号/workspace 维度，不是电脑维度。用户换 Mac 或 Windows，只要使用同一 workspace 的 ONE Key，就应继续使用已经授权的得到连接。
- Launcher/Bridge 更新与知识平台授权分开。新增平台、修改服务端 Connector 或召回逻辑通常只需部署网页/服务端；只有本地执行器协议变化才需要 Launcher/Bridge 更新。
- 不要把第三方 access token 写入 U 盘。U 盘丢失时作废 ONE Key，不应通过复制 U 盘来复制第三方连接。

## 七、新平台的标准落地流程

### 7.1 调研与设计

1. 阅读平台官方文档、官方 SDK/CLI/MCP 源码和服务条款，确认个人授权、企业代授权还是 API Key 模式。
2. 记录授权入口、scope、会员要求、授权有效期、刷新方式、速率限制、数据类型和读写能力。
3. 选定最小只读闭环：连接、搜索/召回、返回引用；暂不做写入、删除和全量同步。
4. 明确服务端固定域名和 API 白名单，禁止任意 URL 转发。

### 7.2 实现

1. 创建独立 Connector adapter，实现 `connect / validate / search` 等最小接口。
2. 把授权状态、凭证和连接元数据绑定 workspace；服务端每次调用重新校验权限。
3. 对 OAuth/Device Flow 实现过期、拒绝、轮询退避、重试、取消和重复授权处理。
4. 对 API/MCP 实现工具白名单、超时、响应大小限制、错误脱敏和不可信内容隔离。
5. 将平台响应规范化为统一的来源、标题、片段、链接、时间和 provider request id；不要把原始上游响应直接交给前端或模型。

### 7.3 验收矩阵

新连接器至少测试以下场景：

- 两个不同平台账号、两个不同 workspace，确认来源绝不串租户。
- 会员/非会员或不同权限账号。
- 授权成功、用户拒绝、授权码过期、重复使用、轮询超时和上游 HTTP 200 业务失败。
- 换电脑、换 Mac/Windows、拔出再插入 ONE Key。
- 连接器超时、限流、网络中断和平台返回恶意/超长内容。
- 凭证轮换、连接断开、撤销授权和重新授权。
- 真实计费边界：只有成功执行且实际消耗模型/平台资源时扣费；失败、取消和重复请求不可重复扣费。

发布前必须通过 TypeScript 检查、相关单元/集成测试、跨 workspace 隔离测试、生产构建和 `git diff --check`。

## 八、版本策略

- V0.1：按需实时召回，保留来源引用，不复制第三方知识到 ONE。
- 后续版本：在明确用户授权、存储、删除、增量同步和费用后，再设计 list/get/sync。
- 连接器应模块化加入，不能把某个平台的字段、scope 或错误码散落在聊天、计费、前端和数据库通用逻辑中。
- 新平台先只读，稳定后再评估写入；写入能力必须有显式用户确认、幂等键、审计日志和回滚策略。

## 九、交接时要提供的材料

每个新平台的交接至少包含：

- 官方文档和版本/日期；
- 授权方式与完整状态机；
- scope、会员和速率限制；
- 凭证字段、加密方式、刷新与撤销；
- Connector adapter 入口和允许的工具/路径白名单；
- 标准化返回结构与引用规则；
- 跨 workspace、跨设备、失败和计费测试记录；
- 已知限制、待平台方确认的问题和回滚方案。

得到大脑的实现是目前唯一经过真实多账号、跨设备验证的样本。其他平台必须单独完成上面的调研和验收，不能直接复制得到的 Client ID、scope、轮询时序或错误处理。
