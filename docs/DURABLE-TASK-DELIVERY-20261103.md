# 持久成果驱动的任务执行与交付改造

## 用户目标与本轮范围

让用户交代任务后能安心离开：系统保留已经做出的成果，自动处理可恢复的临时故障；确实需要用户提供资料、授权或作决定时才打扰。不能将“点一下重试”当作常规人工步骤。以 2026-11-03 用户五项要求与两张截图为验收依据，不能以测试数或任务卡代替真实交付。

已授权实施、验证、提交及上线。原业务稿件、myspace 原任务先只读诊断，不盲目重发；使用独立合成任务做故障与恢复验收。价格、余额、授权不在改动范围。

## 保留的基础

- 继续使用现有模块化单体、线性 workflow、TaskStep 持久检查点、CAS、防重和 durable result inbox。
- 不另建第二套任务引擎或事件总线；不迁移到 Temporal/n8n。
- 历史回执版本及原始证据不改写，成功步骤不重放。
- 每次恢复均核对 workspace/user/operation/revision、当前 Key、来源与目的地授权及用户停止状态。

## 方案取舍

自动重试有次数与时间上限，且按操作效果决定。不能保证外部服务提供 exactly-once；可靠性来自稳定操作身份、保存证据、平台支持的幂等/查询和只读对账。运行中不新增无限模型纠错循环，也不把供应商故障隐瞒成成功。

通用连接器架构参考（已核对官方来源，实际采用范围见下文）：n8n 的节点输入/输出与错误类型、Zapier 的 action schema/perform 与退避。借鉴共同协议，不承诺所有第三方内容格式都无损互通。

### 平台通用架构依据与实际边界

- n8n 的节点使用共同 JSON/binary 数据结构传递结果，各节点保留自己的具体 API 适配，错误分 API 与操作错误：[数据结构](https://docs.n8n.io/data/data-structure/)、[错误处理](https://docs.n8n.io/integrations/creating-nodes/build/reference/error-handling/)。
- Zapier 的触发、搜索、动作有共同 schema、输入/输出字段与 perform 处理器；平台处理调度与退避，各应用实现自己的调用：[Platform CLI](https://docs.zapier.com/platform/build-cli/overview)。
- ONE 采用同样的边界：`operationRecovery.ts` 定义 code-owned 执行/验证/成果引用/恢复事实，实际接入 `TaskStep.operation`，不依赖任何一个平台的正文格式。文档内容转换、Notion 全文比较、文件格式检查仍由对应适配器执行，不用“去掉全部格式”的宽松字符串比较代替完整性验证。
- `workflowPresentation.ts` 是任务动态与详情共用投影，拒绝错 scope/revision/marker/成果引用、重复 checkpoint 和未经 verified 的 Notion 成果。它不返回私有正文、工具参数、供应商编号或凭证。
- 本轮接通的是现有 workflow 的知识读取、模型成果、功能/文件成果和 Notion 交付事实；没有新增第三方连接器。付费搜索、外部图片任务和本机执行仍由各适配器的既有幂等/回执保护管理，不能因公共 envelope 已建立而宣称所有平台均可安全重试。

### 已实现并验证

- 安全读取（得到大脑/已绑定 Notion 只读）在临时超时、限流、5xx 等情况下自动恢复：共最多3次，2s/8s退避，120s恢复启动期限，次数和时间先落盘；权限、参数与用户停止不当作临时故障重试。

- workflow 校验包装保留可信原异常 cause（不枚举/不输出），Key、来源权限、预算等失败继续给准确安全分类，不能被后台重试吞掉。
